# 技能进化专属演出链设计

## 目标

让局内三种主动技能的等级成长与十二种进化在第一次选中后立刻产生可辨识、可复盘的视觉变化。玩家不需要阅读数值，也应能从颜色、轮廓和运动方式分辨“这次构筑选了什么”。本轮只增强表现与可访问性，不改变伤害、治疗、护盾、冷却、能量、敌人、奖励、存档、广告或付费规则。

## 方案选择

本轮比较过三个方向：

1. **Boss 指挥牌**：Boss 可读性高，但会与顶部 HUD、发现票、瞄准区争夺移动端空间。
2. **结算战斗手账**：复盘价值高，但对战斗当下的精致感与构筑反馈改善有限。
3. **技能进化专属演出链**：每次进化选择都改变真实战斗画面，直接回应“图标有冲击、技能随等级成长有明显效果”的目标。

采用第三种。现有规则层已经让十二种进化产生不同战斗效果，但即时画面主要只覆盖等级尾迹、贯礁箭鳍、反棘潮膜、引潮眼、余涡和双潮峰，缺少统一且完整的视觉语言。本轮补齐所有十二种，同时保留既有事件和对象池架构。

## 玩家体验

### 等级成长

三种技能 Rank 1–5 使用同一技能的核心轮廓，但随等级增加层次：

- Rank 1：一个主轮廓，低粒子密度；
- Rank 2：加入第二色描边；
- Rank 3：加入一次外环或分层尾迹；
- Rank 4：增加轮廓尺度与前景层次；
- Rank 5：使用金色高光与完整徽记轮廓，但不增加震屏强度。

等级只影响表现密度、尺寸和层次，具体数量仍受现有高／中／低画质预算控制。低画质必须保留主轮廓和进化色，不允许把进化演出完全裁掉。

## 架构与边界

### 纯签名目录

新增 `web/battle/SkillEvolutionVisualCatalog.ts`，只描述视觉，不持有运行状态。它导出冻结的十二项映射：

```ts
export interface SkillEvolutionVisualSignature {
  readonly id: SkillVariantId;
  readonly skillId: BattleSkillId;
  readonly primary: string;
  readonly secondary: string;
  readonly particleKind: SkillEvolutionParticleKind;
  readonly reducedMotionRingKind: 'static-skill-silhouette';
}

export const SKILL_EVOLUTION_VISUAL_SIGNATURES:
  Readonly<Record<SkillVariantId, SkillEvolutionVisualSignature>>;
```

`SkillEvolutionParticleKind` 也在该文件中定义为十二种进化各自对应的十二类视觉 motif 联合类型；`EffectParticleKind` 通过类型导入并入该联合类型，避免目录反向依赖 `EffectSystem` 形成运行时循环。目录必须完整覆盖 `SKILL_VARIANT_IDS`。颜色和粒子类型由唯一目录维护，`EffectSystem` 与测试不得复制第二套映射。

### 事件与效果系统

`EffectSystem.consume(events, frame)` 继续是视觉状态的唯一生成入口：

- `skill-used` 根据 `frame.skillRanks` 生成等级层次，并遍历该技能已选进化生成即时签名；
- 破泡、牵引、余涡、回能和双潮峰继续使用其真实专用事件；
- 新增 `barrier-emergency-triggered` 事件，只在规则已经成功触发濒海自启时发出，携带 `effectRatio`，不参与数值计算；
- 专用事件出现时不重复生成同一进化的即时占位签名，例如余涡只由 `extreme-vortex-started` 生成完整螺旋；
- 重复消费同一批事件仍遵守现有事件所有权，不额外写存档或遥测。

### 渲染器

`BattleRenderer` 为新增粒子类型使用 Canvas 路径绘制，不新增位图资源：V 形箭、回旋弧、鱼鳍雨线、裂泡碎片、双膜水珠、救援灯、潮眼、回能珠和双峰浪脊。绘制命令必须有稳定 `kind`，以便像素证据和单元测试核对；不把文字烘焙进 Canvas。

### 画质与性能

- 所有粒子继续来自现有对象池，不创建逐帧 DOM。
- 新增签名受 `RenderBudget.particleLimit` 与 `impactLimit` 约束。
- 单次技能事件在高／中／低画质的新增粒子上限分别为 30／20／12；十二种进化同时并不意味着同帧创建十二套满额粒子。
- 每个进化至少有一个优先级不低于 6 的主轮廓，预算裁剪先移除装饰水珠和次级尾迹。
- 不新增持续业务定时器，不改变固定步长模拟，不读取随机数决定签名形状。

## 减少动态与可访问性

`prefers-reduced-motion: reduce` 或游戏设置中的减少动态开启时：

- 不生成位移粒子、旋转螺旋、镜头震动或持续扩张环；
- 每个触发的进化在对应战场位置保留 320–480ms 的静态双轮廓，颜色与普通模式一致；
- 多个进化使用同心但不同半径的静态轮廓，避免互相覆盖；
- 现有技能按钮名称、Rank、进化小图标和冷却文本继续可见；
- 画质设置、减少动态设置不得改变战斗结果、事件顺序或奖励。

## 失败与恢复

- 未知或损坏的进化 ID 会被既有构筑规范化过滤；视觉目录查找不到时跳过表现，不中断战斗。
- 粒子池耗尽时保留高优先级主轮廓，省略低优先级装饰。
- 可选位图加载失败不影响本轮 Canvas 签名；本轮不新增图片依赖。
- 场景卸载、战斗失败和返回车站继续通过现有 `EffectSystem.reset()` 清空所有签名，不把上一局演出带入下一局。

## 验证

### 目录与单元测试

- 十二个 `SkillVariantId` 全部且只出现一次；主色、辅助色、粒子类型和所属技能冻结且匹配权威目录。
- Rank 1–5 的层次单调增加，同时低画质不超过 12 个新增粒子。
- 每个进化的真实触发事件生成独有 `kind` 和颜色；同技能多进化同时保留各自主轮廓。
- 濒海自启只在实际自动触发时发出专用事件，手动屏障不发出。
- 减少动态时十二种进化均只有静态轮廓、无镜头振幅、无位移粒子，战斗状态与结果保持一致。

### 渲染与像素证据

- `RecordingPainter` 验证十二类专属 Canvas 命令具有正确层级、形状数量和非零边界，其中已有四类继续使用稳定命令名并强化形状契约。
- 像素证据至少覆盖分汐 V 形、回潮弧、暴雨扇面、破泡碎片、双膜、救援灯、潮眼和双峰，拒绝实心矩形或越界大面积覆盖。
- 360／390／412／430 宽度不出现横向溢出，签名不遮挡顶部 HUD、速度／暂停、奖励互动或底部技能。

### 真实 Chrome

- 仅在精确 `e2e=1` 下通过权威精通存档、固定种子和真实升级选择，分别在三个隔离战斗中取得齐射、屏障、极潮各一个代表进化；不增加直接改写局内构筑的测试后门。
- 真实点击对应技能后，通过 Canvas 前后像素差异、技能按钮进化图标和 E2E 诊断中的真实效果 `kind` 核对签名，随后继续战斗。十二种完整矩阵由纯目录、效果系统、渲染命令和像素证据测试覆盖。
- 390×844 至少完成其中一局正常构筑路径，验证选择前后签名变化且终局仍为胜利。
- 减少动态媒体模拟下重跑三个代表技能，验证静态轮廓仍可辨识、镜头不移动、DOM 控件与文本不消失。
- 普通 URL 不暴露任何 E2E 夹具；既有四视口、两局胜利、资源预算和经济断言继续通过。

## 本轮边界

不新增技能、进化、货币、奖励、成就、声音资产、皮肤、付费商品或存档字段；不调整任何数值平衡；不重做 Boss HUD、结算手账或全局视觉主题。若后续要添加音效签名，必须作为独立版本评估资源预算、混音和移动端自动播放限制。
